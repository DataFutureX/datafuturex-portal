# 技术门户审核

## 何时使用

- 评审现有门户/文档站
- 改版前摸底、上线前检查、对比最佳实践

## 工作流

```
审核进度:
- [ ] 1. 收集入口（首页、导航、搜索、文档、控制台）
- [ ] 2. 按维度打分并记录证据
- [ ] 3. 输出问题清单（按严重级别）
- [ ] 4. 给出可执行的修复优先级
```

### 1. 收集

快速打开并记录：首页、主导航每项落点、文档首页、任意能力页、搜索「不存在的词」、移动宽度 375px。

有代码库则同时扫：路由表、导航配置、docs 目录、布局组件。

### 2. 审核维度

对照 [checklist.md](checklist.md)，每项标记：通过 / 部分 / 失败 / 不适用，并附文件路径或 URL 证据。

维度：

1. **定位与首屏** — 是否像门户入口而非仪表盘/营销堆砌
2. **信息架构** — 导航 ≤ 6、任务可达、无孤儿页
3. **文档质量** — 快速开始、结构、示例、死链
4. **搜索与发现** — 搜索可见、空态、关键词可命中
5. **一致性** — 术语、视觉、CTA 文案
6. **a11y / 性能** — 语义、键盘、首屏重量

### 3. 输出格式

```markdown
# 技术门户审核报告

## 结论
（1–2 句：能否支撑开发者完成「发现 → 学会 → 使用」）

## 严重问题
- [P0] … — 证据：… — 建议：…

## 应改进
- [P1] …

## 可选优化
- [P2] …

## 已做得好
- …

## 建议修复顺序
1. …
2. …
```

严重级别：

- **P0**：主路径断裂（无文档入口、死链、无法开始）
- **P1**：可完成但成本高（IA 混乱、无搜索、示例不可用）
- **P2**：体验与质量（文案、a11y 细节、性能）

### 4. 约束

- 只报告可验证问题，不空谈「建议加强赋能」
- 每条建议对应具体改法（改导航项 / 补页面 / 改组件）
- 尊重现有设计系统，审核「门户有效性」而非强行换肤
